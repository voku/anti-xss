# :secret: AntiXSS

"Cross-site scripting (XSS) is a type of computer security vulnerability typically found in Web applications. XSS enables 
attackers to inject client-side script into Web pages viewed by other users. A cross-site scripting vulnerability may be 
used by attackers to bypass access controls such as the same origin policy. Cross-site scripting carried out on websites 
accounted for roughly 84% of all security vulnerabilities documented by Symantec as of 2007." - http://en.wikipedia.org/wiki/Cross-site_scripting

### Supported output contexts

`xss_clean()` returns an HTML fragment for the **HTML body context** (between tags, e.g. `<div><?= $clean ?></div>`).
It is not an encoder for other contexts, and its output is **not** safe there without additional, context-specific
handling:

- **Attribute values**: the output can contain quotes and (harmless) tags, so escape it for the attribute, e.g.
  `htmlspecialchars($clean, ENT_QUOTES)` in a quoted attribute; never use it in an **unquoted** attribute.
- **URLs** (`href`, `src`, `action`, ...): plain text like `data:text/html,...` is kept, so validate the scheme
  (e.g. allow only `http` / `https`) instead of relying on `xss_clean()`.
- **JavaScript** (`<script>`, event handlers, `javascript:` URLs) and **CSS** (`<style>`, `style` attributes): not
  supported; use JSON encoding / a CSS-specific allowlist.

See the [OWASP XSS Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)
for context-specific output encoding.

### Event handler attributes

Since 4.1.50, every attribute whose name is `on` + ASCII letters and that has a value is removed, e.g. `onclick`, but
also events that are not on any list (like Safari's `ongesturestart`) or that browsers add in the future. The list of
event names (`_never_allowed_on_events_afterwards`) is not needed for this anymore.

Scope and limits of this rule:

- Only attribute *names* are matched, with the rules of the HTML tokenizer. Text and attribute values are kept,
  e.g. `<p title="onreading mode">`, `data-onclick="..."`, `class="onboarding"`, `on:click` (Svelte), `on-click`,
  `on_load`, `onfoo1` (no browser executes these names). An event handler attribute without a value (`<div onfoo>`)
  is kept, too: it does nothing.
- The context of a `<` is not parsed: the rule is checked from *every* `<` + ASCII letter, also inside of comments,
  `<textarea>`, `<script>` or attribute values (e.g. `<p title="<b onfoo=1>">` becomes `<p title="&lt;b >">`). This is
  conservative on purpose: the browser can see a tag there (`<textarea><p title="</textarea><img onfoo=...>">`).
- Inputs with more than 10000 event handlers (or that exceed a linear scan budget) use a more conservative fallback,
  that also removes `on...=` (after whitespace, `/` or a quote) in text. If PCRE fails, the scan still runs (it does
  not use PCRE).
- `removeNeverAllowedOnEventsAfterwards(['onAbort'])` still allows `onabort` (only names that are on the list).

### If PCRE fails

If a regex can not run (e.g. `pcre.backtrack_limit` exhausted, also with `pcre.jit` disabled), `xss_clean()` fails
closed: the original input is never returned unchecked. A step whose check failed still runs; a removal that failed
uses a non-regex fallback, which removes the dangerous attribute or, as the one terminal fallback, neutralizes the
string: character references are decoded, `:`, `+` and control chars are removed and everything is HTML-encoded
again (also every remaining `&`), so the result has no tag and no URL scheme. The input is reported as XSS. The
guarantees of the [supported output contexts](#supported-output-contexts) do not change. This is lossy on purpose, it only happens if PCRE failed. `tests/PcreFailureTest.php`
checks this (also in separate PHP processes, without the JIT).
- `tests/fixtures/browser-event-handlers.txt` (514 names from the specs and the WebKit, Chromium and Gecko sources,
  generated by `build/event-handlers/extract.py`) is a test resource: every name must be removed. The browser tests
  (`tests/browser/`) check the output in Chromium, Firefox and WebKit.

### Disable automatic encoding changes

This package depends on `voku/portable-utf8`, which sets `default_charset` to `UTF-8` via `ini_set()` during autoloading.

If you need to prevent this behavior, define the following constant **before** loading the Composer autoloader:

```php
define('PORTABLE_UTF8__DISABLE_AUTO_ENCODING', true);
require_once __DIR__ . '/vendor/autoload.php';
```

### Usage:

```php

use voku\helper\AntiXSS;

require_once __DIR__ . '/vendor/autoload.php'; // example path

$antiXss = new AntiXSS();
```

Example 1: (HTML Character)

```php
$harm_string = "Hello, i try to <script>alert('Hack');</script> your site";
$harmless_string = $antiXss->xss_clean($harm_string);

// Hello, i try to alert&#40;'Hack'&#41;; your site
```

Example 2: (Hexadecimal HTML Character)

```php
$harm_string = "<IMG SRC=&#x6A&#x61&#x76&#x61&#x73&#x63&#x72&#x69&#x70&#x74&#x3A&#x61&#x6C&#x65&#x72&#x74&#x28&#x27&#x58&#x53&#x53&#x27&#x29>";
$harmless_string = $antiXss->xss_clean($harm_string);
    
// <IMG >
```
    
Example 3: (Unicode Hex Character)

```php
$harm_string = "<a href='&#x2000;javascript:alert(1)'>CLICK</a>";
$harmless_string = $antiXss->xss_clean($harm_string);
    
// <a >CLICK</a>
```

Example 4: (Unicode Character)

```php
$harm_string = "<a href=\"\u0001java\u0003script:alert(1)\">CLICK<a>";
$harmless_string = $antiXss->xss_clean($harm_string);
    
// <a >CLICK</a>
```

Example 5.1: (non Inline CSS)

```php
$harm_string = '<li style="list-style-image: url(javascript:alert(0))">';
$harmless_string = $antiXss->xss_clean($harm_string);

// <li >
```

Example 5.2: (with Inline CSS)

```php
$harm_string = '<li style="list-style-image: url(javascript:alert(0))">';
$antiXss->removeEvilAttributes(array('style')); // allow style-attributes
$harmless_string = $antiXss->xss_clean($harm_string);

// <li style="list-style-image: url(alert&#40;0&#41;)">
```

Example 6: (check if an string contains a XSS attack)

```php
$harm_string = "\x3cscript src=http://www.example.com/malicious-code.js\x3e\x3c/script\x3e";
$harmless_string = $antiXss->xss_clean($harm_string);

// 

$antiXss->isXssFound(); 

// true
```

Example 7: (allow e.g. iframes)

```php
$harm_string = "<iframe width="560" onclick="alert('xss')" height="315" src="https://www.youtube.com/embed/foobar?rel=0&controls=0&showinfo=0" frameborder="0" allowfullscreen></iframe>";

$antiXss->removeEvilHtmlTags(array('iframe'));

$harmless_string = $antiXss->xss_clean($harm_string);

// <iframe width="560"  height="315" src="https://www.youtube.com/embed/foobar?rel=0&controls=0&showinfo=0" frameborder="0" allowfullscreen></iframe>
```

### Mutation testing with static analysis:

CI runs [Infection](https://infection.github.io/) with PHPStan integration on the PHP 8.3 pull-request job, only for the changed lines (`--git-diff-base=origin/master --git-diff-lines`). It uses `infection.json5.dist`, which requires at least 70% MSI and 70% covered-code MSI; timed-out mutants count as escaped (`timeoutsAsEscaped`) and more than 40 of them fail the run (`maxTimeouts`), so sanitizer loops cannot silently regress.

To run the same toolchain locally on PHP 8.3+:

```bash
composer config --no-plugins allow-plugins.infection/extension-installer true
composer require --dev phpstan/phpstan:^2.1 infection/infection:^0.32.7 --no-update
composer update
XDEBUG_MODE=coverage ./vendor/bin/infection --configuration=infection.json5.dist --git-diff-base=origin/master --git-diff-lines
```
